# Architecture

## Runtime and boundaries

Next.js App Router prerenders the whole application at build time as a static export (`output: "export"`, `trailingSlash: true`, an optional `basePath` from `BASE_PATH`). TypeScript is strict. SQLite persistence is managed by Prisma 7.10.1 with the better-sqlite3 adapter. React 19.3.1 and Next.js 16.4.3 are locked in the package lock; the Prisma 8 prerelease was deliberately not adopted.

Each URL family has its own App Router route under `app/` (for example `app/battles/[slug]/page.tsx`). Route files are thin: they load the catalog, list their records in `generateStaticParams` with `dynamicParams = false` (so unlisted paths get the static 404 page), build metadata and render a view. Views live in `components/views/`, one module per section. The root layout provides a persistent shell. Views receive domain data from `lib/content.ts`; catalogs, maps, quizzes, theme and progress components hydrate as interactive client boundaries. All text uses React escaping; there is no HTML injection or dynamic evaluation of historical content.

`lib/content.ts` reads the seeded database during the build only; the deployed site has no server or database. React `cache` deduplicates repeated reads within a render, including metadata generation. The catalog (127 engagements and studies, 106 commanders, 33 wars, 79 campaigns, 10 courses and 15 exercises) is still read in bulk. That costs only build time, because no page queries at runtime; what matters to readers is how much of it each page carries. Views are server components, so only the props of client components (catalogs, maps, quizzes, progress) travel in a page's route payload; commander pages, for example, chart linked engagements in a career strip instead of rendering a card per study (Napoleon's page fell from 834 KB to 72 KB).

Curated media is the exception to database reads: `lib/media.ts` validates `data/media.json` with Zod at module load, and the library and profile views import it directly. The same records are seeded into `MediaResource`/`HistoricalSource` so the relational source graph stays complete. Course order comes from the `LearningCourse.ordinal` column, and engagements in the same year are ordered by `Battle.ordinal`, which `data/catalog.ts` derives from a date key.

The six collections are curated in `data/collections.ts` rather than the database. Membership is computed from wars and campaigns, so a new study joins its collection without an edit there; each collection's introduction and strategic arc are prose that names member studies, and unit tests check that every name refers to a member.

Pure layout and query logic lives in two modules with unit tests and no React. `lib/logic.ts` holds search matching and ranking, the catalog filters and their query-string form, sorting, collection membership and the career-strip layout. `lib/atlas.ts` holds the atlas regions, marker grouping by screen distance, zoom framing and the fan-out of markers that no zoom separates, and the route-map layout that numbers a campaign's or collection's engagements in date order and merges labels until none overlap.

The schema stores explicit relational links plus validated JSON editorial/read projections. Server views consume those projections for simple type-safe rendering. The seed writes both forms in one transaction. Editing a projection directly without its relationship rows is unsupported; editorial source files and the seed are the update path.

## Design decisions

- **Plain CSS and reusable components:** bespoke editorial styling avoids unnecessary component/theme dependencies. CSS variables, breakpoints and native controls provide consistent dark/light and responsive behavior. Tailwind and shadcn are not used.
- **Subtle motion:** `components/motion.tsx` loads Motion's DOM features through `LazyMotion` (about 35 KB gzipped). `Reveal` fades home-page sections up as they scroll into view; `FadeIn` eases in a new timeline phase and quiz or decision feedback. Prerendered content is never hidden: only blocks that start below the fold are hidden, and only after JavaScript runs. A block is revealed once it has entered the viewport or been scrolled past, so fast jumps cannot leave it hidden. With reduced motion, nothing is hidden or moved.
- **SVG rather than network tiles:** a bundled Natural Earth world atlas keeps the core experience available offline and eliminates API keys, external tile failures and tracking. The atlas draws the 110m coastline first and loads the 50m one only when a reader zooms in; route maps on campaign and collection pages are server-rendered SVG that use the coarse coastline for frames wider than 20 degrees. Approximate atlas locations are distinct from conceptual battle replay geometry, and a route line shows date order, not an army's path.
- **Self-hosted fonts and original SVGs:** `app/fonts.ts` defines four Open Font License families through `next/font/google`, which self-hosts them; there is no runtime font service and no unlicensed artwork. Content pages remain usable when external publishers are unreachable.
- **Opt-in external media:** YouTube players use `youtube-nocookie.com` and are created only after the reader presses a load button. Portrait images are served through the Next.js image optimizer, restricted by `images.remotePatterns` to one archive path, and replaced by an attributed text fallback on error.
- **Browser-local progress:** `lib/persistence.ts` is the replaceable persistence boundary. Versioned data includes bookmarks, recent visits, scores, choices and theme. Invalid JSON, incompatible versions, blocked storage and unsafe stored link targets are handled defensively.
- **No authentication or write API:** the local MVP does not need public mutation endpoints. Content updates occur through versioned files and a transactional seed. Account synchronization should introduce authorization and server validation as a separate phase.

## Navigation and failures

The layout is persistent across navigation. The server waits for route resolution before returning a page, allowing missing records to return a genuine HTTP 404. A root loading boundary was removed after browser tests showed it began streaming a 200 response before invalid-slug resolution. Main navigation instead provides inline pending feedback with `useLinkStatus`. Catalog inputs remain disabled until hydration attaches their handlers, avoiding lost early input on slower browsers. Empty catalogs, unavailable media, storage failures and runtime errors each have contextual messages.

`lib/metadata.ts` builds each page's title, description, canonical URL and Open Graph and Twitter fields. The root layout sets `metadataBase` from `SITE_URL`, which includes the GitHub Pages base path, so root-relative canonical paths resolve to full public URLs. `app/sitemap.ts` lists every content page. No `robots.txt` is generated: crawlers only read it at a domain root, which a project site does not control. Reading bookmarks do not affect server content. Daily challenge rotation follows Europe/Warsaw calendar days.

## Deployment

The site is published to GitHub Pages by `.github/workflows/deploy.yml`, which builds with `BASE_PATH=/<repository-name>/` and uploads `out/`. Query-string state cannot be rendered on a static host, so the search page, battle catalog and atlas render their default state at build time and apply their parameters in the browser (`useSearchParams` inside a `Suspense` boundary whose fallback is the prerendered default): `?q=` and `?type=` on the search page; `q`, `era`, `region`, `kind`, `war`, `campaign`, `commander`, `collection`, `sort` and `view` on the catalog, which writes its state back to the address with `history.replaceState` so a filtered view can be shared; and `?battle=` on the atlas. The video tab is a separate page, `/library/videos/`. Search forms use `next/form`, which applies the base path. `scripts/serve-static.mjs` reproduces Pages behavior locally and for Playwright.

If a server is needed later (accounts, writes), the compatible shape is a Node process with a persistent database and backups behind an HTTPS proxy. Horizontal scale would require an appropriate database strategy. A PostgreSQL migration changes the provider, driver adapter, connection configuration and migration history; the logical entity graph can remain.

## Performance and remaining work

The app requires no tile requests or third-party font requests and does not autoplay animations. Two font files are preloaded; Motion adds about 35 KB gzipped to the home page's JavaScript. The build prerenders 441 pages plus the not-found page and `sitemap.xml`; the static export is about 105 MB, mostly prerendered pages and route payloads (each study carries its full analysis and replay). Replay playback is explicitly started and cleaned up on unmount. Reduced-motion preferences disable CSS transitions. Original vector artwork scales without raster downloads. Route-specific database projections, smaller per-page payloads and a production Lighthouse run are future performance work; no unmeasured score is claimed.
